### Проблемы сервиса

11. Теоретически, для значений метрик с типом ```Counter``` может произойти переполнение переменной
12. Если воспринимать количество воркеров при отправке запросов на сервер как количество одновременно исходящих запросов
    на сервер
    (*т.е. как заданное требование к инкременту / логику, а не только как пропускную способность агента при отправке
    метрик*),
    то количество воркеров (RateLimit) привязывается к PollInterval и ReportInterval.
    А конкретно к значению, вычисляемому по формуле: ```ReportInterval / PollInterval```**, с округлением вверх**.
    А также косвенно к таймауту клиента при отправке запроса и стратегии retry-сервиса.
    Это создаёт ряд ограничений:
    - **Количество воркеров не может быть меньше чем ```ReportInterval / PollInterval```**. Иначе приложение при сборе
      метрик
      будет пропускать пачки данных из-за переполнения очереди с метриками (что критично для метрик типа
      ```Counter```).\
      Произойдёт это потому что канал для общения горутин **Сбора метрик** и **Отправки метрик**, по сути, является ещё
      очередью.
      При малой пропускной способности при **Отправке метрик** (*что равно ```RateLimit``` / количеству воркеров*)
      очередь не будет успевать опустошаться.
      После чего в первые минуты работы приложения горутина **Сбора метрик** будет повисать при попытке записать данные
      в канал.\
      Пример: При значениях по умолчанию: **Сбор метрик** раз в 2 секунды, **Отправка метрик** - раз в 10 секунд, —
      **Сбор метрик** успеет отработать 5 раз до **Отправки метрик**. Собранные пачки метрик хранятся в канале.
      Если количество воркеров равно, скажем, 2, то с каждым циклом **Отправки метрик** длина очереди будет расти на 3
      пачки данных.
    - Верхнее значение количества воркеров тоже необходимо выбирать более тщательно.
      Оно зависит от **таймаута клиента** на запрос к серверу и **стратегии отправки повторных запросов**.
      Количество воркеров должно быть чуть больше минимального значения, опять же, для того,
      чтобы очередь не переполнялась из-за временной недоступности сервера, например.
      Однако это не критично, поэтому особого внимания в этом **MD** уделять не буду.
13. Необходимо заложить либо дополнительное количество воркеров для горутины **Отправки метрик**,
    либо дополнительный объём канала с метриками для общения горутин, на случай кратковременного отключения сервера.
    Иначе произойдёт ситуация, описанная в пункте выше: из-за накапливаемого эффекта, когда воркеры не успевают
    отправлять все метрики из очереди, очередь рано или поздно переполнится, из-за чего приложение будет пропускать
    данные.
